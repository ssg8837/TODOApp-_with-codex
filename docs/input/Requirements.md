# 기능 요구사항

상태: 초안

## 1. 문서 목적

이 문서는 PRD에 정의된 제품 기능을 구현 가능한 수준까지 상세화한다.

각 기능은 다음 항목을 기준으로 정의한다.

- 사용자 동작
- 입력값
- 출력
- 유효성 규칙
- 빈 상태
- 로딩 상태
- 오류 처리
- 데이터 저장 및 삭제
- 완료 조건

요구사항이 미확정인 항목은 임의로 화면 또는 데이터 계약을 확정하지 않는다.

## 2. 확정된 기능

## 2.1 TODO 등록

```text
기능명:
TODO 등록

목적:
사용자가 특정 날짜에 수행할 새로운 TODO를 등록한다.

사용자 흐름:
1. TODO 목록 화면에서 추가 기능을 선택한다.
2. 등록 화면이 표시된다.
3. 제목과 날짜를 입력한다.
4. 필요하면 시간, 종류, 알림을 지정한다.
5. 저장을 선택한다.
6. 저장 성공 후 TODO 목록으로 돌아간다.

입력:
- 제목
- 날짜
- 시간
- 종류
- 알림

출력:
- 신규 TODO
- 연결된 Reminder

유효성 규칙:
- 제목은 필수이다.
- 공백만 존재하는 제목은 허용하지 않는다.
- 날짜는 필수이다.
- 시간은 선택이다.
- 종류는 현재 정책 확정 전까지 선택값으로 취급한다.
- 시간이 없는 경우 알림을 지정할 수 없다.
- 하나의 TODO에 1일 전과 15분 전 알림을 동시에 지정할 수 있다.

빈 상태:
- 신규 등록 화면은 입력값이 없는 초기 상태로 표시한다.
- 날짜는 화면 진입 경로에 따라 현재 선택 날짜를 기본값으로 사용할 수 있다.

로딩 상태:
- 저장 중 중복 저장이 발생하지 않도록 한다.
- 일반적인 로컬 저장에서 불필요한 전체 화면 로딩을 표시하지 않는다.

오류 처리:
- 제목이 없으면 저장하지 않고 입력 안내를 표시한다.
- 날짜가 없으면 저장하지 않고 입력 안내를 표시한다.
- 저장 실패 시 입력 내용을 유지하고 오류 메시지를 표시한다.
- 알림 권한 문제로 TODO 자체 저장을 실패시키지 않는다.

데이터 저장:
- Todo를 로컬 DB에 저장한다.
- 선택한 Reminder를 로컬 DB에 저장한다.
- 알림 설정이 존재하면 저장 성공 후 시스템 알람을 등록한다.

완료 조건:
- 유효한 입력으로 TODO를 등록할 수 있다.
- 등록된 TODO가 선택 날짜 목록에 표시된다.
- 앱 재실행 후에도 데이터가 존재한다.
```

## 2.2 TODO 수정

```text
기능명:
TODO 수정

목적:
등록된 TODO의 내용을 변경한다.

사용자 흐름:
1. 사용자가 기존 TODO를 선택한다.
2. 수정 화면이 표시된다.
3. 기존 데이터가 입력값으로 표시된다.
4. 사용자가 원하는 값을 변경한다.
5. 저장한다.
6. 변경 내용이 목록에 반영된다.

입력:
- TODO ID
- 제목
- 날짜
- 시간
- 종류
- 알림

출력:
- 수정된 TODO
- 수정된 Reminder

유효성 규칙:
- 등록과 동일한 입력 검증을 적용한다.
- 존재하지 않는 TODO ID는 수정할 수 없다.

빈 상태:
- 정상적인 수정 진입에서는 기존 데이터가 표시되어야 한다.

로딩 상태:
- 대상 데이터 조회 중 필요한 경우 화면 로딩 상태를 표시한다.
- 저장 중 중복 저장을 방지한다.

오류 처리:
- TODO를 찾을 수 없으면 사용자에게 안내하고 목록으로 돌아갈 수 있어야 한다.
- 저장 실패 시 사용자가 수정한 입력값을 가능한 한 유지한다.

데이터 저장:
- 기존 Todo를 갱신한다.
- Reminder 변경 사항을 반영한다.
- 날짜, 시간 또는 Reminder가 변경된 경우 기존 시스템 알람을 취소하고 다시 등록한다.

완료 조건:
- 수정한 값이 목록에 반영된다.
- 앱 재실행 후 수정된 값이 유지된다.
- 변경된 알림 시간이 시스템 스케줄에 반영된다.
```

## 2.3 TODO 삭제

```text
기능명:
TODO 삭제

목적:
더 이상 필요하지 않은 TODO를 제거한다.

사용자 흐름:
1. 사용자가 TODO 삭제 기능을 선택한다.
2. 삭제 확인 UI가 표시된다.
3. 사용자가 삭제를 확정한다.
4. TODO가 삭제된다.

입력:
- TODO ID
- 사용자 삭제 확인

출력:
- 삭제된 TODO가 목록에서 제거된다.

유효성 규칙:
- 명시적인 사용자 확인 없이 영구 삭제하지 않는다.
- 존재하지 않는 TODO에 대한 삭제 요청은 안전하게 처리한다.

빈 상태:
- 삭제 후 목록이 비면 해당 날짜의 빈 상태 UI를 표시한다.

로딩 상태:
- 삭제 중 동일 삭제 요청이 반복되지 않도록 한다.

오류 처리:
- 삭제 실패 시 기존 TODO를 화면에서 임의로 제거하지 않는다.
- 사용자에게 삭제 실패를 안내한다.

데이터 저장:
- Todo를 삭제한다.
- 연결된 Reminder를 삭제한다.
- 등록된 미래 시스템 알람을 취소한다.

완료 조건:
- 삭제한 TODO가 목록에서 사라진다.
- 재실행 후 다시 나타나지 않는다.
- 연결된 Reminder 및 시스템 알람이 남지 않는다.
```

## 2.4 TODO 완료/미완료 변경

```text
기능명:
TODO 완료 상태 변경

목적:
TODO의 수행 여부를 관리한다.

사용자 흐름:
1. 사용자가 TODO의 완료 체크를 선택한다.
2. TODO가 완료 상태로 변경된다.
3. 다시 선택하면 미완료 상태로 되돌릴 수 있다.

입력:
- TODO ID
- 완료 여부

출력:
- 변경된 완료 상태

유효성 규칙:
- 완료 여부는 true 또는 false로 관리한다.

빈 상태:
- 해당 없음

로딩 상태:
- 로컬 상태 변경은 즉시 반영하는 것을 기본으로 한다.
- 저장 실패 시 데이터와 화면 상태가 불일치하지 않도록 복구한다.

오류 처리:
- 저장 실패 시 사용자에게 안내한다.

데이터 저장:
- Todo.isCompleted를 갱신한다.

완료 조건:
- 완료/미완료 상태가 즉시 화면에 반영된다.
- 앱 재실행 후에도 상태가 유지된다.
- 미완료 필터가 적용 중인 경우 완료 처리된 TODO가 목록에서 제외된다.
```

완료 시 미래 알림을 취소할지 여부는 미확정이다.

## 2.5 날짜별 TODO 조회

```text
기능명:
날짜별 TODO 조회

목적:
사용자가 특정 날짜에 등록된 TODO만 확인한다.

사용자 흐름:
1. 앱을 실행한다.
2. 오늘 날짜가 기본 선택된다.
3. 사용자가 이전 또는 다음 날짜로 이동한다.
4. 선택한 날짜의 TODO가 표시된다.

입력:
- 선택 날짜

출력:
- 해당 날짜의 TODO 목록

유효성 규칙:
- 날짜는 항상 유효한 달력 날짜여야 한다.

빈 상태:
- 해당 날짜에 TODO가 없으면 빈 상태 안내를 표시한다.

로딩 상태:
- 로컬 DB 조회가 즉시 완료되는 경우 별도 전체 화면 로딩을 표시하지 않는다.

오류 처리:
- 조회 실패 시 사용자에게 목록을 불러오지 못했음을 안내한다.

데이터 저장:
- 날짜 선택 자체의 영속화 여부는 MVP 요구사항에 포함하지 않는다.

완료 조건:
- 선택한 날짜의 TODO만 표시된다.
- 앱 최초 실행 시 오늘 날짜가 표시된다.
```

## 2.6 종류 생성

```text
기능명:
종류 생성

목적:
사용자가 자신만의 TODO 분류를 만든다.

사용자 흐름:
1. 종류 관리 화면으로 이동한다.
2. 종류 추가를 선택한다.
3. 이름을 입력한다.
4. 저장한다.

입력:
- 종류 이름

출력:
- 신규 Category

유효성 규칙:
- 이름은 빈 문자열일 수 없다.
- 공백만 존재하는 이름은 허용하지 않는다.
- 이름 중복 허용 여부는 미확정이다.

빈 상태:
- 종류가 없으면 종류가 없음을 안내하고 추가 기능을 제공한다.

로딩 상태:
- 저장 중 중복 저장을 방지한다.

오류 처리:
- 저장 실패 시 입력한 이름을 유지하고 오류를 안내한다.

데이터 저장:
- Category를 로컬 DB에 저장한다.

완료 조건:
- 생성한 종류가 종류 목록에 표시된다.
- TODO 등록/수정 화면에서 선택할 수 있다.
- 앱 재실행 후에도 유지된다.
```

## 2.7 종류 수정

```text
기능명:
종류 수정

목적:
사용자가 생성한 종류의 이름을 변경한다.

사용자 흐름:
1. 종류 관리 화면에서 수정 대상을 선택한다.
2. 이름을 변경한다.
3. 저장한다.

입력:
- Category ID
- 변경할 이름

출력:
- 수정된 Category

유효성 규칙:
- 이름은 빈 문자열일 수 없다.
- 존재하지 않는 Category ID는 수정할 수 없다.

빈 상태:
- 해당 없음

로딩 상태:
- 저장 중 중복 요청을 방지한다.

오류 처리:
- 수정 실패 시 기존 값을 유지하고 오류를 안내한다.

데이터 저장:
- Category 이름을 갱신한다.

완료 조건:
- 변경된 이름이 종류 목록에 표시된다.
- 해당 종류를 사용하는 TODO에도 변경된 이름이 표시된다.
- 재실행 후 유지된다.
```

## 2.8 종류 삭제

```text
기능명:
종류 삭제

목적:
더 이상 사용하지 않는 종류를 제거한다.

사용자 흐름:
1. 사용자가 종류 삭제를 선택한다.
2. 삭제 확인 UI를 표시한다.
3. 사용자가 삭제를 확정한다.
4. 종류를 삭제한다.

입력:
- Category ID
- 사용자 삭제 확인

출력:
- 삭제된 종류가 목록에서 제거된다.

유효성 규칙:
- 명시적인 삭제 확인이 필요하다.
- 사용 중인 종류를 삭제할 때 Todo를 어떻게 처리할지는 미확정이다.

빈 상태:
- 마지막 종류 삭제 후 종류 없음 상태를 표시한다.

로딩 상태:
- 삭제 중 중복 요청을 방지한다.

오류 처리:
- 삭제 실패 시 기존 종류를 유지하고 안내한다.

데이터 저장:
- Category를 삭제한다.
- Todo와의 관계 처리는 정책 확정 후 구현한다.

완료 조건:
- 확정된 삭제 정책에 따라 Category와 연결 Todo가 일관된 상태를 유지한다.
```

이 기능은 `사용 중인 종류 삭제 정책`이 확정되기 전까지 구현을 완료한 것으로 간주하지 않는다.

## 2.9 종류별 필터

```text
기능명:
종류별 필터

목적:
선택한 종류의 TODO만 확인한다.

사용자 흐름:
1. TODO 목록에서 종류 필터를 선택한다.
2. 원하는 종류를 선택한다.
3. 해당 종류의 TODO만 표시된다.
4. 전체를 선택하면 종류 필터를 해제한다.

입력:
- Category ID 또는 전체

출력:
- 필터링된 TODO 목록

유효성 규칙:
- 존재하는 Category만 필터 대상으로 사용할 수 있다.

빈 상태:
- 조건에 해당하는 TODO가 없으면 필터 결과 없음 상태를 표시한다.

로딩 상태:
- 별도의 전체 화면 로딩은 기본적으로 사용하지 않는다.

오류 처리:
- 조회 실패 시 사용자에게 안내한다.

데이터 저장:
- 필터 선택값의 앱 재실행 간 영속화는 MVP 필수 요구사항이 아니다.

완료 조건:
- 선택한 종류의 TODO만 표시된다.
- 전체 선택 시 모든 종류의 TODO가 다시 표시된다.
```

```text
- 별도의 전체 화면 로딩은 기본적으로 사용하지 않는다.

데이터 저장:
- 필터 선택값의 앱 재실행 간 영속화는 MVP 필수 요구사항이 아니다.

완료 조건:
- 활성화 시 미완료 TODO만 표시된다.
- 종류 필터와 동시에 정상 동작한다.
```

## 2.11 복합 필터

```text
기능명:
복합 필터

목적:
날짜, 종류, 완료 여부 조건을 동시에 적용한다.

사용자 흐름:
1. 날짜를 선택한다.
2. 필요하면 종류를 선택한다.
3. 필요하면 미완료 필터를 활성화한다.
4. 모든 활성 조건을 만족하는 TODO를 표시한다.

입력:
- 날짜
- Category ID 또는 전체
- incompleteOnly

출력:
- 조건을 모두 만족하는 TODO 목록

유효성 규칙:
- 필터 조건은 AND 조건으로 적용한다.

빈 상태:
- 결과가 없으면 조건에 해당하는 TODO가 없음을 표시한다.

로딩 상태:
- 일반 로컬 조회에서 별도의 전체 화면 로딩은 사용하지 않는다.

오류 처리:
- 조회 실패 시 사용자에게 안내한다.

완료 조건:
예를 들어
날짜 = 2026-09-01
종류 = 업무
미완료 = true
인 경우 세 조건을 모두 만족하는 TODO만 표시된다.
```

## 2.12 TODO 알림 설정

```text
기능명:
TODO 알림 설정

목적:
사용자가 TODO 예정 시점 전에 Android 알림을 받는다.

사용자 흐름:
1. TODO에 날짜와 시간을 지정한다.
2. 알림 옵션을 선택한다.
3. TODO를 저장한다.
4. 시스템 알람이 등록된다.
5. 예정된 시점에 Android 알림이 표시된다.

입력:
- TODO 예정 날짜
- TODO 예정 시간
- 1일 전 여부
- 15분 전 여부

출력:
- Reminder
- Android 시스템 알람
- Android Notification

유효성 규칙:
- TODO 시간이 없으면 알림을 설정할 수 없다.
- 하나의 TODO에 1일 전과 15분 전을 동시에 설정할 수 있다.
- Reminder는 TODO 예정 시간보다 이전 시점을 의미한다.
- 계산 결과가 이미 과거인 경우의 정책은 미확정이다.

빈 상태:
- 알림 미선택 상태를 허용한다.

로딩 상태:
- 알람 등록은 저장 과정에서 처리한다.
- 알람 스케줄 실패로 UI가 무한 로딩 상태가 되어서는 안 된다.

오류 처리:
- 알림 표시 권한이 없으면 사용자에게 안내한다.
- 정확한 알람 권한/접근이 필요한 환경에서는 사용 가능 여부를 확인한다.
- 알람 등록 실패 시 TODO 저장 여부와 사용자 안내 정책을 일관되게 처리한다.

데이터 저장:
- Reminder를 로컬 DB에 저장한다.
- 시스템 Alarm은 DB 데이터와 재구성 가능해야 한다.

완료 조건:
- 선택한 Reminder가 DB에 저장된다.
- 시스템에 해당 알람이 등록된다.
- 알람 시간이 되면 TODO를 식별할 수 있는 알림이 표시된다.
```

## 2.13 앱 재실행 후 데이터 유지

```text
기능명:
데이터 영속화

목적:
앱 종료와 관계없이 사용자의 TODO 데이터를 유지한다.

사용자 흐름:
1. 사용자가 TODO와 종류를 등록한다.
2. 앱을 종료한다.
3. 앱을 다시 실행한다.
4. 기존 데이터가 표시된다.

입력:
- 기존 저장 데이터

출력:
- 복원된 TODO
- 복원된 Category
- 복원된 Reminder

유효성 규칙:
- DB 데이터가 화면 상태의 기준(Source of Truth)이 된다.

빈 상태:
- 최초 실행 또는 데이터가 없는 경우 빈 상태를 표시한다.

로딩 상태:
- 초기 DB 조회 상태를 안전하게 처리한다.

오류 처리:
- DB 접근 실패 시 앱이 비정상 종료되지 않고 오류 상태를 표시한다.

데이터 저장:
- Room을 사용한다.

완료 조건:
- 앱 프로세스를 종료한 후 다시 실행해도 데이터가 유지된다.
```

## 3. 알림 관련 추가 조건

### 알림 예정 시간 계산

```text
알림시각 = TODO 예정일시 - 사전알림분
```

예:

```text
TODO:
2026-09-05 14:00

1일 전:
2026-09-04 14:00

15분 전:
2026-09-05 13:45
```

### TODO 수정
다음 값이 바뀌면 기존 Alarm을 취소하고 다시 등록한다.

- 날짜
- 시간
- Reminder

### TODO 삭제
- 시스템 Alarm 취소
- Reminder 삭제
- Todo 삭제

### 기기 재부팅
저장된 Reminder를 기준으로 필요한 미래 Alarm을 다시 등록할 수 있어야 한다.

## 4. 공통 오류 안내 원칙

내부 구현 정보를 사용자에게 직접 노출하지 않는다.

사용자 메시지 예:

```text

TODO를 저장하지 못했습니다. 다시 시도해주세요.

TODO를 삭제하지 못했습니다. 다시 시도해주세요.

알림을 사용하려면 알림 권한이 필요합니다.
```

Stack trace, DB 오류 코드 등의 내부 정보는 사용자 메시지에 직접 표시하지 않는다.

## 5. 데이터 저장 및 삭제 정책

- TODO는 로컬 DB에 저장한다.
- Category는 로컬 DB에 저장한다.
- Reminder는 로컬 DB에 저장한다.
- 앱 종료만으로 데이터를 삭제하지 않는다.
- TODO 삭제 시 연결된 Reminder를 함께 삭제한다.
- TODO 삭제 시 등록된 시스템 Alarm을 취소한다.
- Category 삭제 시 기존 Todo 처리 방식은 별도 확정한다.
- 앱 자체를 제거한 경우 Android의 앱 데이터 정책에 따라 로컬 데이터가 삭제될 수 있다.

## 7. 구현 제한

- 요구사항이 미정인 기능은 화면이나 데이터 계약을 임의로 확정하지 않는다.
- 삭제처럼 복구하기 어려운 동작에는 명시적인 사용자 확인 요구사항이 필요하다.
- UI 구현 편의를 이유로 기능 요구사항을 변경하지 않는다.
- PRD와 Requirements가 충돌할 경우 구현 전에 요구사항을 정리한다.
- TRD와 기능 요구사항이 충돌할 경우 제품 요구사항을 만족하는 기술 대안을 검토한다.
- 요구사항에 존재하지 않는 기능을 AI Agent가 임의로 추가하지 않는다.
- 미확정 요구사항은 추측하여 구현하지 않는다.

## 8. 미확정 요구사항

다음 항목은 구현 전에 확정해야 한다.

### TODO
- 종류 없는 TODO 허용 여부
- 과거 날짜의 TODO 등록 허용 여부
- 과거 시간의 TODO 등록 허용 여부
- TODO 기본 정렬 순서
- 시간이 없는 TODO와 시간이 있는 TODO의 정렬 순서
- 같은 시간 TODO의 정렬 순서

### Category
- 같은 이름의 종류 중복 허용 여부
- 사용 중인 종류 삭제 허용 여부
- 종류 삭제 시 기존 TODO의 처리 방법
- 종류 정렬 방식
- 종류별 색상 필요 여부

### Reminder
- 완료 처리 시 미래 알림을 취소할지 여부
- 완료 → 미완료 변경 시 취소한 알림을 다시 등록할지 여부
- 이미 지난 알림 시간이 포함된 TODO 저장 시 처리
- 정확한 Alarm이 필수인지 허용 오차가 존재하는지
- 정확한 Alarm 권한을 사용자가 허용하지 않은 경우의 fallback
- 재부팅 중 지나간 알림 처리

### UI
- 날짜 선택 UI
- TODO 삭제 확인 UI
- Category 삭제 확인 UI
- 알림 권한 요청 시점 및 안내 UI
